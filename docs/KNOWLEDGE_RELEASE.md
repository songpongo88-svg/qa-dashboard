# T&C and user guide releases

The app, bundled guide and build metadata are shipped in the same Vite artifact. A failed build cannot publish a new guide. `npm run build` checks `guide:check` at the start of prebuild, before the existing patches generate deployment source. The review fingerprint describes the committed source, not the generated files.

Before every release:

1. Review the actual UI change against `src/knowledge/manual.json`. Update affected chapters, steps, images, timestamps and release notes. Permission/context mappings are part of the deployed code.
2. Run tests and review the affected screens or PDF output. Content fixes made in the guide editor are validated and recorded in `qa_user_guide_history`; they apply only when their base chapter hash matches the bundled chapter. A new deployment that changes that chapter uses its new bundled content until the edit is reviewed again. Unchanged chapters retain compatible published edits.
3. Record the review explicitly:

   ```sh
   npm run guide:review -- --reason "Describe the verified user-facing change" --chapters "evaluation,process"
   # For a verified change that does not affect usage:
   npm run guide:review -- --reason "Explain why the existing guide remains accurate" --no-content-change
   ```

4. Commit `docs/guide-release-review.json` with the code and guide. Run `npm run build` from a clean checkout and publish through the existing GitHub main → Vercel flow. Do not commit incidental source changes generated by the existing prebuild scripts. The source fingerprint check fails for unreviewed source, build-plugin, style, script or workflow changes. It verifies a recorded review, not the semantic accuracy of prose; the release author must actually review the instructions and images.

Terms are in `src/knowledge/terms.json`. Never edit an already-published version in place. Bump the version and effective date, provide its change summary, and record a new review. The review ledger prevents reusing a version for different wording. The gate reappears for the new version; previous acknowledgements remain unchanged.

`qa_terms_acceptances/{encodedUsername}__{version}` stores the wording snapshot, SHA-256 content hash, identity, server timestamp, optional explicitly chosen signature and deployment commit. Only the acceptance action writes; there is no migration/backfill, delegated acceptance, or write to monthly signatures. The first write wins in a transaction. No acceptance is cached as a substitute for a successful server read/write. PDF bytes are generated on demand from that immutable snapshot; the source evidence is in Firestore and the downloaded PDF is saved by the user's browser.

T&C Management follows existing Manage Users and team scope. Guide editing follows Manage QA Rubric. Writes validate the existing central session and stored role. These modules use the project's existing Firestore access model; they do not change authentication or database security rules.

Local verification: `npm run test:knowledge` uses isolated in-memory data, never production acceptance or signature records. Kanit font files and their OFL license are included in `public/fonts` so PDF exports do not depend on external font hosting.
